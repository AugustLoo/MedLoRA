01 · Starting point

Two sentences left over from last week

Last week's report ended with one claim and one worry. Every experiment this week was built around those two sentences.

The claim: the model's reluctance to say "uncertain" does not come from the base model or from continued pre-training. It comes from the SLAKE fine-tuning data, where every answer is a single word. The evidence was that models with CPT only, and no SFT, were the best calibrated. If this is right, adding three-class examples back into the fine-tuning data should remove the problem, with no need for an extra DPO stage.

The worry: the general-ability probe, TextVQA, has only 300 questions and uses short-answer OCR. Its format is too close to our fine-tuning output, so it might miss forgetting. We needed a more sensitive probe.

"So alignment should change the SFT data mix, not add another stage."
"TextVQA's short-answer questions are too close to our SFT output format to detect degradation."

— Week 1 report, sections 07 and 03

02 · Method

To practise on the exam, first cut the exam in half

Only PubMedQA has three-class examples, and it is also our reliability evaluation set. A score earned by practising on the exam does not count.

We split it in half, stratified by label, with a fixed seed of 42. The split file is committed to git, and the script refuses to regenerate it once it exists. One half goes into training; the other half is only ever used for scoring. Per-question predictions from earlier models were stored, so we filter them by the split and recompute. Every model is measured with the same ruler, and no inference was repeated.

Practice half · training
500

Class-balanced sampling: 33 / 100 / 300 per class gives 99 / 300 / 900 examples in total. There are only 55 unique "maybe" items, so they repeat about 0.6 / 1.8 / 5.5 times at the three budgets. These are mixed into the 4,919 SLAKE examples for one fine-tuning run. All other hyper-parameters match experiment A exactly. The only variable is the replay count.

Exam half · never trained on
500

Gold answers 276 yes / 169 no / 55 maybe. Every PubMedQA number on this page comes from this half only.

03 · Main result

How the answer distribution moved back toward the truth

The grey hatched bars are the gold distribution. Scroll down to see how the predicted distribution changes with each batch of replay data.

PubMedQA predicted yes / no / maybe · held-out half, 500 questions
01 / 05

Base model: leans yes and guesses maybe

The untuned model answers 320 / 97 / 83. That is 44 too many yes and 72 too few no. It says maybe 83 times but is right only 7 times. That is guessing, not caution.

02 / 05

Fine-tuning alone: the bias gets worse

Experiment A re-run on the server, with zero replay: 356 / 112 / 32. "Maybe" halves, and no→yes errors rise from 42 to 63, more than before any fine-tuning. Last week's claim is independently reproduced here: short-answer fine-tuning systematically pushes the model toward yes.

03 / 05

Add 99: it overshoots at once

197 / 183 / 120. With only 99 examples (33 per class, each "maybe" item seen at most once), macro-F1 rises from 51.5 to 57.4, and it gets 23 "maybe" questions right, the most of any run. But it answers yes only 197 times against 276 gold. Yes recall drops to 60.9, and plain accuracy, 64.6, is lower than with no replay. It has learned that no and maybe exist as options, but not yet when to use them.

04 / 05

Add 300: pulled back, still overshooting

228 / 178 / 94. Macro-F1 jumps from 51.5 to 60.5, and no→yes errors fall from 63 to 14, below the base model. The cost is only 228 yes answers against 276 gold, and yes recall falls from 91.7 to 69.9. Both seeds (42 and 43) land here, with yes recall of 69.9 and 72.1.

05 / 05

Add 900: closest to the truth, only 0.8 more gain

269 / 151 / 80 (seed 43: 287 / 162 / 51), the distribution closest to gold. Macro-F1 is 61.1 / 60.7 and yes recall 79.7 / 84.4. Yes recall moves back monotonically with the replay budget, 60.9 → 71.0 → 82.1, and never reverses across four runs. But going from 300 to 900 adds only +0.77 (mean of both ends), the same size as run-to-run noise.

All six runs at 0 / 99 / 300 / 900 replay were trained on the server in bf16 without quantisation, with identical hyper-parameters. They differ only in replay count (and seed), so they can be compared directly.
04 · Answering an objection

It is not just guessing "uncertain" more often

The question most likely to come up: haven't you just tuned it to say "uncertain" more often?

The base model already said maybe 83 times and was right 7 times. With 300 examples it says maybe 94 times and is right 21 times. With 900 it says maybe 80 times and is right 19 times. About the same number of attempts, three times as many correct. Precision and recall improve together across all three classes. The 99-example run marks the boundary: it says maybe 120 times and is right 23 times. The class is restored, but the model has not learned when to use it, and plain accuracy is lower than with no replay. Accuracy rises monotonically with the budget, 64.6 → 69.6 → 73.0. A small budget shifts the prior; only a larger budget teaches discrimination. This is an interpretation, not a proof.

Adding the two dangerous error types together gives 48 at 99, 46 at 300 and 45 at 900. They are all level; only the split differs. At 300, no→yes is pushed very low but yes→no rises; at 900 both sides are balanced. Which is better depends on the use case, and the report does not pick a single "optimum". A second seed (43) repeated the 300 point: no→yes 12, yes→no 30, yes recall 72.1, almost identical to seed 42's 14 / 32 / 69.9. The over-correction is a property of the budget, not an accident of one run.

05 · Rigour

To keep a single variable, experiment A was re-run

Experiment A was originally trained on a Kaggle T4 with 4-bit quantisation. The replay experiments were trained on the server's 5090 in bf16 without quantisation. Three things differ, so the two cannot be subtracted directly.

So A was fully re-run under the same conditions on the same GPU (A-server). All five metrics agree to within half a point, and even the final validation loss is 0.145 versus 0.1446. Changing hardware and quantisation reproduced the training trajectory. This run also serves as the zero-replay point on the curve, and partly substitutes for a second random seed: an independent reproduction with different hardware, precision and quantisation.

06 · Cost

What exactly is being lost

The gain is measured. What about the cost? Scroll down: two forgetting curves appear in turn, and the second one overturns last week's worry.

General ability vs replay count · accuracy %
01 / 04

TextVQA goes down

At 0 / 99 / 300 / 900 replay examples, TextVQA is 83.56 → 82.78 → 82.45 → 81.83. The 300 and 900 points are means of two seeds; the small hollow dots are the individual seeds. Every replay point is below zero replay, and the 900 end is 1.73 lower, about five questions. It looks as if replay is eating general ability.

02 / 04

First, take fine-tuning itself out

The base model scores 84.22, and SLAKE fine-tuning alone brings it to 83.56, a drop of 0.66, which is noise. So the further drop is caused by replay, not by fine-tuning. The attribution is clean.

03 / 04

Second probe: no movement at all

MMBench: 500 four-way multiple-choice questions covering 20 ability dimensions. At 0 / 99 / 300 / 900 replay: 87.40 / 87.20 / 87.20 / 87.80 (means). Everything is within ±0.6 of zero replay. One point is five questions, so this is noise. Across four points and six runs, the largest per-category change is one question.

04 / 04

So the loss is format, not ability

Replay injects one-word yes / no / maybe answers. Short-answer OCR questions are sensitive to that shift in the output distribution; multiple-choice questions are not. Earlier, half of the TextVQA regressions turned out to be surface variants such as one penny → 1 penny, which fits. Last week we worried TextVQA would underestimate forgetting. It is the other way round: it overestimates it.

Main task, SLAKE: at 99 and 300 replay, closed accuracy does not drop (+0 / +0.48, in both seeds) and open EM rises. At 900, closed accuracy falls about one point in both seeds (84.13 / 84.62), while open EM rises 0.6 to 1.7. That is a small, stable cost at the 900 budget.
07 · Trade-off

How much replay is enough

This is the most practical finding of the week: fixing calibration needs far less data than expected.

The first 99 examples buy +5.99 macro-F1, about 60% of the gain. At 300 the gain is +8.69 (mean of two seeds), about 90%. The next 600 examples add only +0.77, the same size as run-to-run noise. The marginal return per hundred examples falls 6.0 → 1.3 → 0.13, a fifty-fold drop. The cost appears only in short-answer format; the end points are clear and the middle is within noise.

+8.69300 · mean of two seeds

Almost all the gain at once

99 examples already give +5.99; going to 900 adds only +0.77. In the 99 run each "maybe" item is seen at most once, yet its maybe recall is the highest, so the fix does not rely on memorisation. There is no need to run 1,800, where each "maybe" item would repeat 11 times.

±0SLAKE · 300

No main-task cost

Closed +0.48, open +0.47, in both seeds. At 900, closed accuracy is about one point lower in both seeds (84.13 / 84.62 against ≥ 85.34 everywhere else), a stable cost of about 4–7 questions. Open accuracy is never below zero replay at any replay point.

300 or 900

No single optimum

To keep general ability and the main task intact, choose 300: 90% of the gain, about 3 TextVQA questions. For the most balanced classes and the highest plain accuracy, choose 900: about one closed-question point and about 5 TextVQA questions. The report states the trade-off and leaves the choice to the user.

08 · Conclusion

Stage 3 has been redefined

In the project pipeline, "alignment" is by default a third training stage, usually DPO. The last two weeks show that in this pipeline it is not needed.

The reliability problem is not inherited from pre-training; stage 2 creates it. Last week's CPT-only evaluation showed the first half of that sentence, and this week's replay experiments show the second half. Adding another stage would mean using a new stage to repair what the previous one broke. Stage 3 is therefore redefined as the design of the fine-tuning data mix, and DPO becomes a fallback.

One more point is worth making. The mechanism inferred last week from the CPT-only evaluation predicted this week's result before it was tested. That says more than the result itself: we understand the mechanism rather than chasing numbers. And the fact that the TextVQA worry was overturned shows the evaluation corrects itself instead of reporting only the flattering results.
